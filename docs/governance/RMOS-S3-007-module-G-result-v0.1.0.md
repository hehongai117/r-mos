### 3.1 G-AUTH-02 的诚实边界

复用了模块 F 在 `4102bd3b` 建立的 `class_id` 参数，**未另写判定**。

但 Codex 如实报告了一个限制：**训练会话没有独立的 `class_id` 列**，
只有当会话快照显式携带 `class_id` 时才能推出所属班级。
这是边界说明，不是回避——快照不带时退回原粒度。

> 若要彻底解决，需给 `training_sessions` 补班级维度。
> 那是数据模型改动，不在本模块范围，已登记。

### 3.2 G-MEM-01 推翻了架构文档的一处判定

S1-001 §4.2 曾把 `memory_hub` 的 Redis fallback 判为「**内存合理**」——
理由是它只是降级路径。**实测推翻**：它会向另一 `user_id` 返回同一会话的业务数据。

修法是给降级键加用户维度（`_short_term_key(session_id, user_id)`），
**没有改成落库**——落库属 M-19 整体处置，在模块 G 内夹带会变成跨模块架构改动。

**S1-001 §4.2 已同步更正**，判定改为「内存可接受，**但键必须带用户维度**」。

> 这是架构文档第二次被实测修正（第一次是 S3-01 试点推翻「模块划分能表达分层」）。
> **判定写在文档里不等于成立**，每条都要有行为级证据。

### 3.3 G-KNOW-01：过滤生效 ≠ 可用性正确

模块 C 给 `KnowledgeHub.search` 加了 `viewer_user_id` 做归属过滤，
缺省为 `None` 时只返回公共条目。模块 G 调用时**没传**，
于是校内私有知识被一并滤掉——**过滤是生效了，能力却掉了**。

修完专门有断言证明同校私有知识**能**被检索到。

> 这类缺陷只有跨模块改造时才会暴露：上游把守卫加严，下游调用方没跟上。
> 后续模块凡是调用 B／C／H 的地方都应查一遍参数是否补全。
